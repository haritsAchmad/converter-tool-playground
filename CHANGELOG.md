## [Unreleased]

### Added

- Experimental PDF → DOCX plain-text extraction (the roadmap's "Experimental PDF → Office extraction" item), pure Go, always available. Deliberately scoped to text only, explicitly not layout-preserving and says so everywhere it's documented: no columns, tables, fonts, or image placement, just each page's text as one paragraph per line with a page break between pages. Text comes from `github.com/ledongthuc/pdf`'s `GetPlainText`—added after confirming pdfcpu (already a dependency here) has no plain-text extraction API of its own, only raw content-stream/image/font/page extraction that would need a hand-written PDF content-stream interpreter to turn into readable text. Verified the same way oksvg/rasterx were before depending on it: pure Go, BSD-3-Clause, no `net`/`net/http`/`os/exec` import in the package, no `govulncheck` advisories; its `GetPlainText` already recovers from a parse panic internally, and `convertPDFToDocx` adds its own outer `recover` around the rest of the package's calls (`Open`/`NumPage`/`Page`) since that guarantee doesn't necessarily extend there. The DOCX itself is hand-built—this codebase only ever validated/read OOXML before, never wrote it—with the three parts ECMA-376 requires for a WordprocessingML package, XML-escaped via `encoding/xml`. A PDF with no extractable text at all (scanned/image-only pages, or a font encoding the library doesn't handle) fails the job outright with a clear reason rather than silently producing an empty-looking file. No LibreOffice was available in this environment to verify the output actually opens in Word/LibreOffice (same gap already noted for the Impress/PPTX and ODF corpus tests), so verification instead independently re-parses the generated `word/document.xml` with a second `encoding/xml` reader and confirms real extracted text (from a hand-built multi-page PDF fixture with genuine `BT`/`Tj` operators, not copy-pasted strings) survives intact and in order. A first attempt at building that PDF fixture via pdfcpu's own `AddTextWatermarksFile` was tried and found empirically not to work for this purpose: its stamped text renders through a Form XObject the page only `/Do`-invokes, which `ledongthuc/pdf`'s content-stream interpreter doesn't descend into.

- SVG → PNG/JPEG conversion, pure Go, always available (no external tool). This is two independent, deliberately separate layers, matching the roadmap's own wording ("SVG only after a dedicated sanitizer and rasterization boundary"): `validateSVG` (the sanitizer) parses the upload with `encoding/xml` and rejects outright a non-`<svg>` root, any `<script>`/`<foreignObject>`/`<image>`/SMIL-animation/`<iframe>`/`<object>`/`<embed>`/`<audio>`/`<video>` element, any inline event-handler attribute (`onload=`, `onclick=`, ...), any `javascript:` URI, any `href`/`xlink:href` that isn't a same-document `#fragment` or a safe inline `data:` image (reusing `isSafeDataURI`, shared with the Markdown/HTML→PDF validator), any CSS `url()` (in a `style=` attribute or a `<style>` block, reusing `validateCSSForPDF`) to anything but a safe `data:` URI, and a leading `DOCTYPE` outright (a real SVG has no legitimate use for one). `convertSVG` (the rasterization boundary) renders with `github.com/srwiley/oksvg`+`rasterx`, a pure-Go SVG renderer verified directly against its source to implement only path/shape/gradient/group elements plus a same-document-only `<use>`—no scripting, no `<image>`, no `foreignObject`, no SMIL, and no `net`/`net/http`/`os/exec` import anywhere in either package—so even something that slipped past the sanitizer can only fail to render, never execute or fetch anything, independent of the sanitizer by construction of the library rather than by trusting it. The raster canvas is sized from the SVG's own `viewBox`/width/height (falling back to a fixed 512×512 square when none is declared, since oksvg's attribute parser—confirmed against its source—does strip a `px` suffix before `strconv.ParseFloat`, so this only triggers for a genuinely dimensionless root element) and bounded by the same `maxImageDecodedPixels` decompression-bomb ceiling an ordinary PNG/JPEG upload already gets, checked before the canvas is allocated. `govulncheck` found no advisories against either new dependency. WebP isn't offered as a target the same way it isn't for PDF→image: no pure-Go WebP encoder exists in this project's dependencies. Verified with real hostile-SVG fixtures (script injection, event handlers, plain and HTML-entity-encoded `javascript:` URIs, an external `<image>`/`<use>` reference, external CSS `@import`/`url()`, a DOCTYPE-based entity-bomb payload) confirmed rejected, real benign fixtures confirmed rasterized (pixel-level color assertions against the decoded PNG/JPEG output, not just "no error"), and a full HTTP create-to-worker-to-completed pipeline test.

- Video conversion (MP4 H.264/AAC, WebM VP8/VP9 + Opus/Vorbis) via the same `ffmpeg`/`ffprobe` engine and hardening audio already used—`ffmpegHardeningArgs` (renamed from `audioProbeArgs` now that it's genuinely shared: `-protocol_whitelist file`, pinned `-analyzeduration`/`-probesize`, forced `-f <format>`) applies unchanged, and `ffprobeStream` gained `Width`/`Height` fields both formats' validators use. Deliberately narrower than audio, the reason video was scoped out of that earlier slice in the first place: exactly one video stream and at most one audio stream (silent video is valid; any subtitle/data stream, or a second of either, is rejected outright—no cover-art-style exception the way audio has for attached pictures), a 720p pixel ceiling, and a 60-second duration cap, so a job stays plausibly within this project's existing job-timeout model rather than needing a video-specific one (actual encode time still depends on content complexity and CPU, not just duration/resolution—size `CONVERTBOX_JOB_TIMEOUT` accordingly). `mp4`/`webm` aren't literally ffmpeg's own input-side demuxer names (the real ones are the combined `mov,mp4,m4a,3gp,3g2,mj2` and `matroska,webm`), but empirically confirmed against a real ffmpeg binary that its format-name resolution accepts them as input aliases into those anyway. libx264/libvpx/libopus availability was confirmed directly against this project's exact `alpine:3.22` `ffmpeg-libavcodec` package dependencies (checked on pkgs.alpinelinux.org)—no Dockerfile change needed, the `ffmpeg` package audio already added bundles all of it. Verified end to end with real ffmpeg/ffprobe (installed locally for this): command structure was prototyped live on the CLI before any Go code was written, and the regression suite includes a real MP4↔WebM round-trip conversion and a full HTTP create-to-worker-to-completed pipeline test, using fixtures ffmpeg's own `lavfi` test sources generate (hand-building minimal-but-valid video bytes isn't practical the way it is for WAV).

- Network egress denial for `worker` and `pdf-worker` in `compose.yaml`: both now sit on `backend`, a new Docker network declared `internal: true`, which gets no default gateway configured at all—no route to the internet or the rest of the LAN, only to `redis`, their one real dependency. `api` joins both `backend` (to reach `redis`) and the normal `default` network so its published port keeps working. This closes the network-layer gap the PDF worker isolation and Office/Markdown-HTML→PDF entries above explicitly deferred. Verified against a real `docker compose up` (Docker Desktop was started for this, with confirmation first): from inside a running `worker`/`pdf-worker` container, `wget http://1.1.1.1` fails with "Network unreachable," while a real CSV→JSON job and a real PDF→PNG job both still flow end to end through `api`'s published port, `redis`, and back out to download.

### Fixed

- Three findings from an external code review of the network-egress/video/SVG/PDF→DOCX commits:
  - **[P1]** `convertSVG` computed `int64(w)*int64(h)` against the SVG's declared `viewBox` dimensions without any bound on `w`/`h` individually first. A `viewBox="0 0 4294967296 4294967296"` (2^32 on each side) makes that product wrap around to exactly 0 mod 2^64—sailing straight past the `maxImageDecodedPixels` check—and `image.NewRGBA` then panics on the actual huge dimensions ("NewRGBA Rectangle has huge or negative dimensions"), reproduced directly. No `recover()` wraps a worker goroutine's call chain the way the HTTP handlers' `recoverer` middleware does, so this panic crashes the whole worker process, not just the one job—a real, uploadable-file DoS. Fixed by validating `icon.ViewBox.W`/`.H` as `float64` and bounding each individually by `maxImageDecodedPixels` *before* ever converting to `int` or multiplying (converting an out-of-range float to `int` is itself implementation-defined per the Go spec, a second reason not to do it first): both are then guaranteed `<=1e8`, so the existing product check can never overflow regardless of aspect ratio.
  - **[P2]** `convertPDFToDocx` checked `ctx.Err()` only at the top of each page-extraction loop iteration, never after the loop or during `writeDocx`. A cancellation/timeout arriving during or right after the *last* page's extraction—or entirely within `writeDocx` itself—went unobserved, and the job was reported `completed` regardless. Reproduced directly with an already-expired context reaching that point in the code. Fixed by checking `ctx.Err()` once more right after the extraction loop (before `writeDocx` is even called) and by having `writeDocx` itself return `ctx.Err()` after finishing its write instead of a bare `nil`—the same two-checks-around-one-operation shape `zipRenderedPages` already uses for the identical reason. `writeDocx`'s signature grew a `ctx context.Context` parameter accordingly.
  - **[P2]** `validateSVG` reused `validateCSSForPDF` (built for `validateHTMLForPDF`'s data:-only policy) for an SVG's `style=""` attributes and `<style>` element content, so `style="fill:url(#g)"` referencing a `<linearGradient id="g">` defined earlier in the very same document—completely ordinary, standard SVG, not an edge case—was wrongly rejected, with a "HTML contains a CSS url()..." error message from a code path that has nothing to do with HTML. Fixed with a new `validateCSSForSVG`, using the same local-`#fragment`-or-safe-`data:` policy `isSafeSVGHref` already applies to a bare `href`/`xlink:href`, instead of `validateCSSForPDF`'s data:-only one.

- `store.persist()`'s final `os.Rename` (temp file onto `job.json`) had no retry, unlike the read side (`readJobState`/`readWithRetry`, added earlier in this same file for the identical class of problem—see this section further down). On Windows, that rename needs delete access to the destination, which fails with "Access is denied" for as long as any other handle has the file open for reading—which a concurrent status poll's plain `os.ReadFile` does for a short but nonzero window. A failed `persist()` was only logged by every caller, never retried: for a job's *final* Completed/Failed transition specifically, that also skipped `ackJob` entirely (`process()` returns `false`), permanently stranding the on-disk state at whatever its last successful write was—most visibly, status stuck at `processing` forever, since both the status endpoint and the worker's own dequeue always re-read from that file, never from the in-memory pointer a worker keeps mutating after `persist()` returns. Not a hypothetical: found by real, reproducible failures in this SVG feature's own worker-pipeline test under `go test -race`—SVG rasterizes in low single-digit milliseconds, so several `persist()` calls land close together against a 10ms-interval HTTP status poll also reading `job.json`, and instrumenting the `os.Rename` call confirmed "Access is denied" on nearly every run before this fix (and a lower but nonzero rate for the similarly fast CSV→JSON pipeline test, confirming this wasn't SVG-specific). Fixed with a `renameWithRetry` helper (5 attempts, 10ms apart), the write-side counterpart to `readWithRetry`; stress-tested at 20 back-to-back `-race` runs of the SVG pipeline test (0 failures, versus roughly 70% failing before the fix) plus 10 runs each of the CSV, audio, video, and ODF pipeline tests. Added a real-file regression test (`TestRenameWithRetrySucceedsPastConcurrentReader`, an actual concurrent open-then-close reader racing a real `os.Rename`, not a mocked error function) and a persistent-failure test.

- `pdfcpu` tries to create its own on-disk config directory (`~/.config/pdfcpu`) the first time any of its functions run, which panicked with `mkdir /home/app/.config: read-only file system` the moment a real PDF was uploaded to a container running under this project's own `read_only: true` hardening—a bug that `docker compose config` validation could never have caught, only surfaced by the real `docker compose up` run above. Fixed with `api.DisableConfigDir()`, called once from a package `init()` before any pdfcpu call in this codebase can run; this codebase never uses pdfcpu's own config file or custom user fonts, so disabling it outright has no functional downside. Verified by resubmitting the same PDF job successfully after rebuilding the image.

- Audio conversion (MP3, WAV, FLAC, Ogg Vorbis/Opus) via `ffmpeg`/`ffprobe`, appearing only when both are installed (Alpine's `ffmpeg` package, added to the Docker image, bundles both plus the `libmp3lame`/`libvorbis` encoders this needs—confirmed against Alpine's own package dependencies, not assumed). Every upload is probed with `ffprobe` before conversion and rejected unless it has exactly one audio stream on a fixed per-container codec whitelist, a duration under 4 hours, and no extra video/subtitle/data stream other than an attached-picture cover-art image (which real-world MP3/FLAC files commonly carry, and would otherwise be collaterally rejected). Every ffmpeg/ffprobe invocation—both the upload-time probe and the real conversion—forces the exact expected demuxer (`-f mp3`/`wav`/`flac`/`ogg`) and whitelists only the `file` protocol (`-protocol_whitelist file`), closing off a real class of ffmpeg SSRF/local-file-disclosure exploit: a file merely *named* `clip.mp3` but structured as an HLS playlist or a `concat` script can otherwise make ffmpeg fetch an internal `http(s)://` URL or read an arbitrary local file through references embedded inside the file itself, regardless of its extension. `-analyzeduration`/`-probesize` are pinned to explicit values rather than ffmpeg's own version-dependent defaults. See the README's new "FFmpeg hardening" section for the full reasoning. Video is deliberately out of scope for this slice.
- Fixed (temuan review P1, same slice): the shared hardening flags above initially included `-nostdin`, which stops ffmpeg from ever blocking on interactive input—but `-nostdin` is an ffmpeg-CLI-only option `ffprobe` doesn't recognize, so passing it to `ffprobe` made every single audio upload's validation fail outright, before the file was ever actually read. `-nostdin` now only appears in `convertAudio`'s own ffmpeg invocation, not in the flags shared with `validateAudio`'s `ffprobe` call. Verified against `ffprobe`'s own option handling and confirmed by actually installing `ffmpeg`/`ffprobe` and running the audio test suite for real (previously only unit-tested against fixtures and skip-guarded where the tools weren't installed)—`TestValidateAudioAcceptsRealWAV`, `TestConvertAudioEndToEnd` (WAV→MP3/FLAC/Ogg), and the full HTTP `TestAudioJobFlowsThroughWorker` pipeline test all pass against the real binaries.

- Isolated PDF worker: a new `pdf-worker` `CONVERTBOX_MODE` dequeues and renders PDF→image jobs off their own Redis queue (`CONVERTBOX_REDIS_PDF_QUEUE`) exclusively, so a bug in poppler's `pdftoppm` ever getting exploited by a hostile PDF compromises that container alone, not the shared `worker` handling every other conversion (Office/ODF/Markdown/HTML→PDF via LibreOffice, images, structured data). A job's input format decides which queue `api` enqueues it on (`App.queueFor`); `worker(index int, q jobQueue)` now takes the queue it drains as an explicit parameter instead of always reading a single `a.queue` field, so a worker's scope is structural, not just conventional. `standalone` mode reuses one local queue for both roles, since a single process has nothing to isolate a second queue from. `compose.yaml` gains a `pdf-worker` service (same image as `worker`, just a different mode and a lighter resource envelope since it never runs LibreOffice)—**this is a deployment change, not just a code one**: an existing split deployment needs the new service added, or PDF jobs will queue but never get drained, since `worker` no longer picks them up at all. See the README's new "PDF worker isolation" section for exactly what this does and doesn't protect against, and the existing single-instance-per-service caveat (already true of `worker`) that now applies to `pdf-worker` too. `docker compose config` confirms the new service's YAML is valid; a real multi-container run wasn't verified here since the Docker daemon wasn't available in this environment.

- PDF content-disarm check (`validatePDFActiveContent`), completing the content-disarm stage the roadmap had blocked on DOCX/PDF/ODT all landing in 0.3 (DOCX/ODT already got theirs via `validateOOXML`/`validateODF`). Rejects a PDF carrying an embedded JavaScript name tree, an embedded file attachment, or a document-level `/OpenAction`/`/AA`—the mechanisms that fire automatically the instant a document tool opens the file, no click or interaction needed. Runs off the same `pdfcpu` structural-validation pass every PDF upload already went through, now via `api.ReadAndValidate` (which hands back the parsed context) instead of the plain `api.Validate` that threw it away, so this adds no extra parse pass. An embedded file attachment is checked three ways, not just the `/EmbeddedFiles` name tree and `ctx.ListAttachments()`: `validatePDFAnnotationAttachments` also walks every page's `/Annots` for an annotation (most commonly a `/Subtype /FileAttachment` one) carrying its own `/FS`/`/EF`, since that attachment path never has to be registered in the catalog's Names dictionary at all, which neither of the other two checks looks past (temuan review P2). Actions stay scoped to document-level triggers only, though—a Link annotation's own `/A` or a form field's own `/AA`, which only fire on user interaction this service's `pdftoppm`-based rendering never performs, aren't walked, since unlike an attachment those aren't inert data sitting in the file regardless of interaction. The `Names` tree keys and `XRefTable.Names` population timing were checked against `pdfcpu`'s own validation source rather than assumed. Added regression fixtures: hand-built PDFs with a byte-accurate xref table computed from the bytes actually written (not hand-counted offsets), run against `pdfcpu`'s real validator to confirm each is structurally well-formed before asserting it gets rejected for its active content.

- ODT/ODS/ODP → PDF via the same LibreOffice pipeline Office→PDF already uses (`convertOffice`/`convertViaLibreOffice`), always with `pdfMode=""`: those fidelity filter options were verified only against OOXML's filter registry, so `odfFormats` is kept deliberately separate from `officeFormats` rather than silently letting `pdfMode` apply to a pair nobody checked it against. New `validateODF` mirrors `validateOOXML`'s package-safety bounds (entry count, uncompressed size, decompression ratio, zip-slip) and its reject-outright stance on macros (ODF's `Basic/`/`Scripts/` directories, verified against LibreOffice's own documented macro-library layout, rather than OOXML's `vbaProject.bin`) and embedded objects (ODF's numbered `ObjectN/` subpackages rather than OOXML's `/embeddings/`). External resource references (`xlink:href`, checked via a streaming `encoding/xml` decoder rather than a raw-byte regex, for the same entity-decoding-bypass reason `validateHTMLForPDF` does) get a *stricter*, default-deny policy than OOXML's own: every reference outside a `text:a`/`draw:a` element's *own* `href` (temuan review P1: an earlier version exempted every `href` found anywhere inside a hyperlink's subtree, not just the hyperlink element's own target, so an external image nested inside a `draw:a`—e.g. a linked logo—slipped through unchecked) is accepted only when it names a real entry already present in that same, already-validated ZIP package, matched against the href's percent-decoded form (temuan review P2: comparing against the raw, still-encoded text rejected an entirely ordinary reference like `Pictures/my%20photo.png` to a real package entry containing a space)—not merely "not an external URL"—since this codebase found no unambiguous confirmation that every ODF-consuming LibreOffice code path resolves a relative reference purely against the package rather than ever falling through to the filesystem. The package's mandatory first `mimetype` entry (stored, uncompressed, no extra field, per the OASIS spec) is checked at a fixed byte offset at upload time, mirroring the existing PNG/JPEG/OOXML signature checks, and again against the real ZIP entry during structural validation. A real end-to-end LibreOffice conversion test is deferred, same reasoning as the existing Impress/PPTX regression-fixture gap: no LibreOffice-capable dev environment was available to verify a hand-built fixture actually opens.

- Markdown/HTML → PDF via the same headless LibreOffice engine and per-job profile isolation Office→PDF already used, sharing the actual `--convert-to`/profile/verify-output logic through a new `convertViaLibreOffice` helper. Markdown is rendered to HTML first with goldmark in its default *safe* mode (raw HTML embedded in the source, e.g. a `<script>` block, is dropped rather than passed through—verified directly rather than assumed) instead of being handed to LibreOffice directly, since a bundled headless LibreOffice cannot be relied on to have its own Markdown import filter. Because this pair, unlike the existing pure-Go HTML↔Markdown text conversion, actually renders the document with a real layout engine that resolves references, it's gated by a new `validateHTMLForPDF`, which parses the document with `golang.org/x/net/html` (rather than pattern-matching the raw bytes) and rejects `<script>`/`<iframe>`/`<object>`/`<embed>`/`<base>` tags and inline event-handler attributes outright. Every resource reference (`src`/`srcset`/`poster`/`background`/`formaction`/`action`/an `<object>`'s `data`/a `<link>`'s `href`/a CSS `url(...)`) is accepted only as an inline `data:` URI—a default-deny allowlist, not a denylist of known-bad schemes—since LibreOffice resolves a relative or absolute local path against the document's real on-disk location, and a job's per-job working directory is not a sandbox: it can walk into a sibling job's files or anywhere else the worker can read, the same class of risk as the external-URL SSRF this codebase already flags for FFmpeg's network-capable input protocols on the roadmap, just reached through a path instead of a hostname (temuan review P1: an earlier version allowed same-directory-relative references on the mistaken assumption they had nothing to resolve against, and checked the raw HTML text for a `http`/`https`/`ftp`/`file`/`//` prefix, which an HTML-entity-encoded scheme like `src="&#104;ttp://127.0.0.1/probe.png"` slips past—a real parser decodes that the same way LibreOffice's own would before checking it). An ordinary `<a href>` hyperlink is deliberately left alone (its target is never fetched, just embedded as a clickable annotation), mirroring the OOXML validator's own allowance for hyperlink relationships. The accepted `data:` URIs are themselves a closed allowlist of raster image formats (PNG/JPEG/GIF—not WebP, since this codebase has no Go-native WebP decoder to bound its dimensions with, the same reason `validateUpload`'s own decompression-bomb check already skips it), cross-checked against their actual decoded bytes' magic signature (an attacker-declared media-type parameter proves nothing on its own) and bounded to the same declared-dimension ceiling (`maxImageDecodedPixels`) an ordinary PNG/JPEG upload already gets—not simply "any `data:` URI is fine" (temuan review P1, round 3): a `data:text/css;base64,...` stylesheet used to pass that check outright, but LibreOffice parses its *decoded* content as an ordinary stylesheet exactly like a `<style>` block, so a nested external `url(...)` inside it reached LibreOffice's fetch path unchecked; `image/svg+xml` is excluded for the same reason (an SVG can embed its own `<script>`). Confirmed (LibreOffice's own documentation/forums, not guessed) that LibreOffice has no built-in flag to disable external-resource loading during conversion; real defense in depth here still wants the worker's outbound network access denied at the OS/container level, noted on the roadmap as follow-up hardening alongside the same already-noted gap for Office→PDF.
- Per-job attempt cap (`CONVERTBOX_MAX_JOB_ATTEMPTS`, default 3) to stop a poison-pill job from crash-looping forever. `requeueActive()` still unconditionally moves everything in the Redis worker's `:processing` list back onto the main queue on startup, so a job that reliably panics or OOM-kills the worker used to get requeued and re-crash it every single time it was picked up, with no way out. A worker now increments and persists the job's `Attempts` count to `job.json` before it does any conversion work, so the count survives even a crash mid-job; once a job's `Attempts` exceeds the cap on its next pickup, the worker marks it `failed` (`"exceeded max processing attempts"`) and acks it out of `:processing` instead of running the converter again. The counter lives in job state rather than the queue backend, so it applies to the local `standalone` queue too.
- Optional `pdfMode` (`standard` default, or `optimized`) on Office→PDF jobs, surfaced as a selector in the web UI when a DOCX/XLSX/PPTX targets PDF. `optimized` sets LibreOffice's `SinglePageSheets` (Calc: every sheet forced onto one page), `EmbedStandardFonts`, and `ReduceImageResolution`/`MaxImageResolution=150` export filter options; `standard` passes none, unchanged from before this field existed. Filter names and option semantics verified against LibreOffice's own filter registry and documentation, not guessed. Also added this codebase's first regression tests that actually run a real DOCX/XLSX through LibreOffice (previously only OOXML package-structure validation was tested, never an actual conversion)—PPTX coverage stayed at the filter-logic level; see ROADMAP.md for why.
- PDF → PNG/JPEG now renders every page (previously first-page-only), up to a new 300-page validation cap, packaged as a ZIP with one `page-N.<ext>` entry per page. This is a **breaking change** to the output shape for this pair: it used to be a bare image and is now always a ZIP, even for a one-page source, so the API/UI contract stays predictable regardless of page count. Extension resolution for the new `.zip` output is now the single `outputExtension(in, out)` helper shared by job creation *and* `store.reload()`—the latter previously re-derived the expected extension from `formats[out].Extensions[0]` on its own and rejected every PDF→PNG/JPEG job's `.zip` `OutputName` outright, which made both the status endpoint and the worker treat the job as unavailable and silently leave it stuck at `queued` forever instead of converting it. `reload()` also falls back to the pre-ZIP `.png`/`.jpg` extension (`legacyOutputExtensions`) for a job that already **completed** under the old convention, so an already-finished job's status/download stay reachable for the rest of its retention window instead of breaking the moment the new convention shipped—new jobs are unaffected, they still only ever get `.zip`. That legacy fallback is now gated on `Status == Completed` rather than applying to any job whose `OutputName` doesn't match today's extension (temuan review P2): a job still `queued`/`processing` when a Redis worker upgraded has no on-disk output under any extension yet, so `reload()` now migrates its recorded `OutputName`/`OutputPath` to `.zip` instead of trusting a legacy `.png`/`.jpg` name the worker was about to overwrite with ZIP bytes, which used to produce a download that claimed to be an image but wasn't one. Job timeout/cancellation now also reaches the ZIP-packaging step itself, not just `pdftoppm`: `zipRenderedPages` takes `ctx` and checks it before copying each page (also temuan review P2), so a cancelled/timed-out job stops between pages instead of finishing however many hundreds of already-rendered pages remained and holding the worker past its deadline. That per-page check alone still let a cancellation land mid-copy of whichever single page was in flight run to completion and report success—the failure mode a **one-page** PDF hits every time, since it never reaches a second per-page check (temuan review P2, round 2). `copyIntoZip` now copies through a `contextReader` that checks `ctx` on every `Read`, so `io.Copy` aborts mid-chunk instead of finishing the page regardless, and `zipRenderedPages` checks `ctx` once more after `zw.Close()` so a cancellation landing during archive finalization (after every page already copied cleanly) isn't reported as success either. Added store-level regression tests for both the original bug and the compatibility fix, one for the status-gated migration, one proving the ZIP loop stops on a cancelled context, one exercising the per-chunk cancellation deterministically via a synchronizing reader rather than real file timing, and one for the post-finalization check.
- PNG/JPEG/WebP → PDF, wrapping the source image as a single PDF page sized to it at 150 DPI. Implemented with pdfcpu (already a dependency for PDF structural validation) rather than a new external tool, so it's always available.
- Runtime-detected DOCX, XLSX, and PPTX to PDF conversion through headless LibreOffice.
- Bounded OOXML package validation that rejects macros, ActiveX, embedded objects, traversal paths, and external non-hyperlink resources before conversion.

### Changed

- Office conversions use private temporary LibreOffice profiles, and the container includes common metric-compatible fonts.

### Fixed

- `store.reload()`/`store.recover()` now retry reading a job's `job.json` sidecar up to 3 times (10ms apart) on an error that isn't "file doesn't exist", instead of treating any read failure as the job being unavailable. `persist()` writes via a temp file plus `os.Rename`, which is atomic on POSIX but can transiently fail a concurrent reader on Windows with a sharing violation while another process (antivirus, search indexing) has briefly opened the file being replaced—not a real "job not found". Prompted by an intermittent 404 seen once in `TestPDFToImageJobFlowsThroughWorkerReload` under local review (not reproduced again across 100+ isolated reruns and 10 full-suite reruns); this hardens the most plausible cause without weakening the fast-fail path for a genuinely missing file (wrong ID, already expired and removed), which still fails on the first attempt. Added regression tests for the retry/backoff logic itself (`readWithRetry`), exercised against a fake read function rather than trying to reproduce the OS-specific timing.
- Image upload validation now checks the declared width/height from the PNG/JPEG header against a 100-megapixel ceiling before conversion ever decodes the full pixel buffer. Previously `image.DecodeConfig`'s dimensions were read but discarded, so a small file could declare an arbitrarily large image and force a multi-gigabyte allocation on decode—a classic decompression bomb bounded only loosely by the job timeout and container memory limit (i.e., an OOM-kill, not a clean rejection). Added regression tests for both the oversized-dimension rejection and that ordinary images still pass.
- CSV output (from JSON/XML/YAML input) now quote-escapes cells starting with `=`, `+`, `-`, `@`, tab, or CR before writing them, closing an OWASP "CSV Injection" hole: an attacker-controlled field value like `=cmd|' /C calc'!A0` used to reach the exported `.csv` byte-for-byte, ready to run as a formula/DDE command the moment someone opened it in Excel, Sheets, or LibreOffice. Added regression tests, plus tests confirming (they already passed without a code change) that the YAML and JSON decoders reject alias bombs and deeply nested input instead of hanging or exhausting memory.
- `compose.yaml`: the `redis` service dropped all Linux capabilities but the official `redis:8-alpine` entrypoint needs `CAP_SETUID`/`CAP_SETGID` to drop from root to its `redis` (999:1000) user before writing to `/data`. Without those caps it silently kept running as root, which then lacked `CAP_DAC_OVERRIDE` to write into the image's `999:1000`-owned data directory, so `redis-server` failed to create `appendonlydir` and the whole stack refused to start. Fixed by pinning `user: "999:1000"` on the service so it starts as the right identity directly, bypassing the entrypoint's privilege-drop path entirely.

### Added

- PDF → PNG/JPEG conversion (first page, fixed 150 DPI), via poppler's `pdftoppm`, appearing only when it's installed (bundled in the Docker image, optional locally). PDF input is validated by two independent parsers before conversion—a magic-byte check plus a full structural pass with the new `github.com/pdfcpu/pdfcpu` dependency (pure Go, no cgo)—separately from the native renderer that actually processes the file. Added tests covering acceptance of a well-formed PDF, rejection of a fake signature, rejection of a structurally broken PDF that has a real signature, and (skipped unless `pdftoppm` is installed) an actual render round-trip.
- Optional `caddy` reverse-proxy service (`docker compose --profile proxy up`) for TLS termination in front of `api`: [deploy/Caddyfile](deploy/Caddyfile) covers both a public-domain (automatic Let's Encrypt) and an internal/LAN (self-signed, on-demand per-hostname) setup, and blocks `/metrics` on the public listener. Documented in the README's new "Deploying beyond localhost" section, including the trade-off that fronting the API with a proxy collapses per-IP rate limiting into one shared bucket (Caddy's container IP), since `clientIP` deliberately ignores `X-Forwarded-For`.
- Optional shared-secret authentication: when `CONVERTBOX_API_KEY` is set, every `/api/v1/*` and `/metrics` request must send it back as `X-API-Key` (compared in constant time) or gets `401`. `/healthz` and the static web UI stay open. The bundled web UI now prompts for the key on a `401`, remembers it in `localStorage`, and sends it on every request—including downloads, which switched from a plain `<a href>` link to a `fetch` + blob so the header can actually be attached.
- Restart-safe job state: each job persists a `job.json` sidecar next to its files, and the server rebuilds its in-memory job map from disk on startup so status/download keep working after a restart. Jobs still queued or processing at shutdown are recovered as failed since they cannot be resumed.
- Per-IP token-bucket rate limiting on job submission (`CONVERTBOX_RATE_RPS`, `CONVERTBOX_RATE_BURST`) and a concurrent-job quota per IP (`CONVERTBOX_MAX_JOBS_PER_IP`).
- Request IDs (`X-Request-ID`) on every response, structured access logging, Prometheus metrics at `GET /metrics`, and OpenTelemetry HTTP instrumentation wired to the global (no-op by default) tracer provider.
- Initial Go server and embedded responsive web interface.
- Async bounded worker pool with UUID job isolation, deadlines, polling, and downloads.
- CSV, JSON, XML, YAML, PNG, JPEG, Markdown, and HTML conversion.
- Optional ImageMagick-powered WebP support with a restrictive policy.
- Multi-layer upload validation and executable/script rejection.
- Automatic TTL and orphan cleanup constrained to the storage root.
- Non-root, read-only Docker deployment with resource limits.
- Tests, CI, security policy, contributing guide, and roadmap.
