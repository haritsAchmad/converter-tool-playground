# Roadmap

## 0.2 — operational hardening

- [x] Persist minimal job state for restart-safe status reporting.
- [x] Per-IP token-bucket rate limiting and upload quotas.
- [x] Prometheus metrics, request IDs, and OpenTelemetry hooks.
- [x] Layered upload gate: extension chain, magic bytes, MIME, syntax, and active-script rejection.
- [x] Separate API and conversion worker containers with a Redis-backed queue and shared job storage.
- [x] Optional ClamAV stage before the conversion queue; fail closed when enabled.
- [x] Harden the currently-supported structured-data pipeline against known injection/DoS classes: CSV cells are now quote-escaped against formula/DDE injection (OWASP "CSV Injection"), and regression tests confirm the YAML and JSON decoders already reject alias bombs and pathologically deep nesting instead of exhausting resources.
- [x] Bound PNG/JPEG decode memory against a decompression bomb: `image.DecodeConfig`'s declared width/height are now checked against a 100-megapixel ceiling during upload validation, before `image.Decode` ever allocates the full pixel buffer for a conversion.
- [x] Format-specific content-disarm stage for DOCX/PDF/ODT, now that all three landed in 0.3. DOCX (and XLSX/PPTX) and ODT (and ODS/ODP) already got theirs as part of landing those formats: `validateOOXML`/`validateODF` reject macros, embedded objects, and external-non-hyperlink resources at upload time (see the 0.3 entries below). PDF's own equivalent, added here: `validatePDFActiveContent` rejects a PDF carrying an embedded JavaScript name tree, an embedded file attachment, or a document-level `/OpenAction`/`/AA` (additional actions)—the mechanisms that run automatically the instant a document-processing tool opens the file, no user interaction needed. Reuses the same `pdfcpu` structural-validation pass already required for every PDF upload (now via `api.ReadAndValidate`, which returns the parsed `*model.Context` `PageCount`/`Names`/`RootDict` checks need, instead of the plain `api.Validate` that discarded it) rather than a second parse. Deliberately scoped to document-level triggers, not exhaustive: a per-object action (a Link annotation's own `/A`, a form field's own `/AA`) isn't walked, since those only fire on explicit user interaction (clicking, editing) that this service's `pdftoppm`-based rendering pipeline never performs—matching this codebase's existing honesty about narrower-than-ideal reject-lists (see `rejectActiveContent`'s `<?php`/`<?=`-only pair). Verified the exact `Names` tree keys (`JavaScript`, `EmbeddedFiles`) and that `XRefTable.Names` gets populated during validation against `pdfcpu`'s own validation source rather than guessed. Regression fixtures are hand-built PDFs with a byte-accurate xref table computed from the actual bytes written (not hand-counted), and were run against `pdfcpu`'s real validator locally to confirm each one is structurally well-formed, not just assumed to be.
- [x] Poison-pill / dead-letter handling for the Redis-backed queue: `requeueActive()` still unconditionally moves everything from `:processing` back onto the main queue on worker startup, but a job now carries a persisted `Attempts` counter (`job.json`, alongside its other state) that a worker increments and durably persists *before* it touches the file—so the count survives a crash mid-conversion, not just a clean failure. Once `Attempts` exceeds `CONVERTBOX_MAX_JOB_ATTEMPTS` (default 3) on pickup, the worker marks the job `failed` with `"exceeded max processing attempts"` and acks it out of `:processing` without ever running the converter again, instead of requeuing it for another crash. Queue-agnostic by construction (state lives in `job.json`, not in Redis), so it also caps retries for the in-process `standalone` queue.
- [x] Optional shared-secret `X-API-Key` authentication on the API and `/metrics`, with the web UI prompting for and remembering the key.
- [x] Documented reverse-proxy config (TLS termination) for deployments reachable beyond localhost, since the API key alone doesn't protect traffic in transit.

## 0.3 — more engines

- [x] PDF → PNG/JPEG (every page, up to a 300-page cap, fixed DPI) via poppler's `pdftoppm`, gated behind a second, independent structural validation pass (pdfcpu, which also enforces the page cap) so a hostile PDF has to fool two different parsers, not one. Multi-page output is a ZIP with one `page-N.<ext>` entry per page—including for one-page sources, so the output shape is predictable regardless of page count—since a job still produces exactly one output file.
- [ ] Move PDF conversion into its own isolated worker/queue instead of the shared worker pool, for real blast-radius containment if the renderer is ever exploited—deliberately deferred as a lighter first slice; revisit once there's a reason to believe the shared pool isn't enough.
- [x] PDF as an output format, for images: PNG/JPEG/WebP → PDF via pdfcpu's pure-Go image import (no external tool, unlike every other PDF or WebP conversion pair here)—one page, sized to the source image at 150 DPI.
- [x] PDF as an output format, for documents: Markdown/HTML → PDF via the same headless LibreOffice engine and per-job profile isolation Office→PDF uses (`convertViaLibreOffice`, shared by both). Markdown is rendered to HTML first with goldmark in its default *safe* mode (raw HTML in the source is dropped, not passed through) rather than handed to LibreOffice directly, since a bundled headless LibreOffice can't be relied on to have its own Markdown filter. Unlike the existing pure-Go HTML↔Markdown text conversion, this pair actually renders the document with a real layout engine that resolves references, so it's gated by `validateHTMLForPDF`, which parses the document (`golang.org/x/net/html`) rather than pattern-matching the raw bytes and rejects `<script>`/`<iframe>`/`<object>`/`<embed>`/`<base>` tags and inline event handlers outright. Every resource reference (`src`/`srcset`/`poster`/`background`/`formaction`/`action`/`<object>` `data`/`<link>` `href`/CSS `url()`) is accepted only as an inline `data:` URI—not just an external `http(s)` URL blocked, everything else rejected by default—since LibreOffice resolves a relative or absolute local path against the document's real on-disk location and a job's per-job working directory is not a sandbox (temuan review P1: an earlier version allowed same-directory-relative references on the mistaken assumption they had nothing to resolve against, which missed that `../` can walk into a sibling job's files or anywhere else the worker can read, and checked the raw HTML text for a scheme prefix, which an HTML-entity-encoded `src="&#104;ttp://127.0.0.1/probe.png"` slips past a real parser doesn't). An ordinary `<a href>` hyperlink is left alone, its target never fetched (mirrors the OOXML validator's own hyperlink allowance). The accepted `data:` URIs are themselves a closed allowlist of raster image formats (PNG/JPEG/GIF; not WebP, which this codebase has no Go-native decoder to dimension-bound, the same gap `validateUpload` already has for it), cross-checked against the actual decoded bytes' signature and bounded by the same `maxImageDecodedPixels` ceiling an ordinary image upload gets—accepting *any* `data:` URI isn't enough (temuan review P1, round 3): a `data:text/css;base64,...` stylesheet used to pass that check, but LibreOffice parses its decoded content as an ordinary stylesheet just like a `<style>` block, so a nested external `url(...)` inside it reached LibreOffice's fetch path unchecked; `image/svg+xml` is excluded too, since an SVG can embed its own `<script>`. Real defense in depth still wants the LibreOffice worker denied outbound network access at the OS/container level—no LibreOffice flag exists for this per Ask LibreOffice's own forum; that stays follow-up hardening, same as the egress-denied worker isolation already noted below for Office→PDF. Structured data → PDF is lower priority and not part of this slice.
- [x] DOCX/XLSX/PPTX → PDF via headless LibreOffice with per-job profiles, bounded OOXML package validation, and rejection of macros, embedded objects, and external resources. Dedicated egress-denied worker isolation remains follow-up hardening.
- [x] Office-to-PDF fidelity controls: `pdfMode=standard` (default, no export filter options—today's behavior unchanged) vs `pdfMode=optimized` (`SinglePageSheets` for Calc, `EmbedStandardFonts` and `ReduceImageResolution`/`MaxImageResolution=150` for all three), exposed via the API and a web UI selector shown only for Office→PDF. Verified against LibreOffice's own filter registry and PDF-export-parameters documentation rather than guessed—getting a filter option name wrong means it silently no-ops. Orientation and print-area turned out to *not* be independently controllable via export filter data at all (they're read from the source document's own page style, not overridable at export time), so those aren't part of this—only what's actually achievable shipped, nothing implied by the original wording that wasn't.
  - [x] Regression corpus: real (not placeholder-content) DOCX and multi-sheet XLSX fixtures actually run through LibreOffice—a baseline this codebase didn't have at all before (only OOXML *package-structure* validation was tested, never an actual conversion). Locks in that `optimized` mode's `SinglePageSheets` guarantee holds (a 3-sheet workbook always comes back as exactly 3 PDF pages) and that both modes produce structurally valid PDFs (pdfcpu-validated).
  - [ ] Impress/PPTX regression fixture: skipped for now. A minimal-but-schema-valid PPTX needs a slide → slideLayout → slideMaster → theme relationship chain with real content in each (theme1.xml alone needs a full 12-color scheme, font scheme, and 3-tier fill/line/effect format scheme)—considerably more scaffolding than DOCX/XLSX, and with no local LibreOffice available to verify a hand-built fixture actually opens, shipping one unverified risked a corpus test that's silently wrong rather than useful. The filter name (`impress_pdf_Export`) is verified against LibreOffice's own filter registry and covered by a pure-Go unit test; the conversion code path is 100% shared with DOCX/XLSX. Pick up if/when there's a LibreOffice-capable dev environment to verify a real fixture against, or a maintained minimal-PPTX generator worth depending on.
  - [ ] Writer header/footer overflow and Impress text-fit/slide-layout *checks* (as opposed to the controls above) would need rendering the PDF to pixels and comparing against page bounds—out of scope for this slice, which covers the concrete, filter-data-level controls the roadmap wording anticipated.
- [x] ODT/ODS/ODP → PDF via the same LibreOffice pipeline as Office→PDF (`convertOffice`/`convertViaLibreOffice`, always called with `pdfMode=""` since its fidelity filter options were verified against OOXML's filter registry only—see the Office-to-PDF fidelity controls entry above—not ODF's, so `odfFormats` is deliberately kept separate from `officeFormats` rather than silently inheriting `pdfMode`). `validateODF` is `validateOOXML`'s counterpart: the same entry-count/uncompressed-size/decompression-ratio bounds and zip-slip rejection, adapted to ODF's own package layout—macros live under top-level `Basic/`/`Scripts/` directories (verified against the OpenOffice/LibreOffice Basic IDE's documented library storage convention) rather than a `vbaProject.bin` part, and an embedded object is a numbered `ObjectN/` subpackage rather than an `/embeddings/` part, both rejected outright. External resource references get a *stricter* policy than OOXML's own denylist-of-external-non-hyperlink-resources: this codebase found no unambiguous confirmation that every ODF-consuming LibreOffice code path resolves a relative `xlink:href` purely against the package's own entries rather than ever falling through to the filesystem the way the Markdown/HTML→PDF path turned out to—so every `xlink:href` outside a `text:a`/`draw:a` element's *own* `href` is accepted only when it names a real entry already present in that same, already-validated ZIP package, never anything with a scheme, a leading `/`, or a `..` segment, matched against its percent-decoded form. Two temuan review rounds tightened this further: round 1 exempted every `href` anywhere inside a hyperlink's subtree rather than just the hyperlink element's own target, so an external image nested inside a `draw:a` (a linked logo, say) slipped through; round 2 compared against the href's raw, still-encoded text, so an ordinary reference like `Pictures/my%20photo.png` to a real package entry containing a space was wrongly rejected. The package's own mandatory first `mimetype` entry (stored, uncompressed, no extra field, per the OASIS OpenDocument Package spec) is checked twice: a fixed-byte-offset signature check at upload time (mirroring the existing PNG/JPEG/OOXML magic-byte checks) and again against the real ZIP entry during structural validation. A real end-to-end LibreOffice conversion corpus test is deferred for the same reason the Impress/PPTX regression fixture above was: no LibreOffice-capable dev environment was available here to verify a hand-built ODT/ODS/ODP fixture actually opens, and shipping one unverified risks a corpus test that's silently wrong rather than useful; static package validation and a fake-LibreOffice "reaches conversion" pipeline test cover what can be verified without one.
- [ ] Experimental PDF → Office extraction; do not advertise this as layout-perfect or implement it by merely opening PDF in LibreOffice Draw.
- [ ] Audio/video through FFmpeg with probe limits and codec whitelists. Also disable FFmpeg's network-capable input protocols (`-protocol_whitelist file,pipe` or equivalent)—by default it can be told to fetch from `http(s)://`, `rtmp://`, `concat:`, etc. via a crafted filename or an embedded reference inside some container formats, which turns a "convert this file" request into an SSRF/internal-network-probe primitive if left open.
- [ ] SVG only after a dedicated sanitizer and rasterization boundary.

## Later

- S3-compatible temporary storage with bucket lifecycle rules.
- Accounts, quotas, history, and PostgreSQL.
- Webhooks/API keys and multi-instance deployment.

Format additions are gated on a threat model, deterministic resource limits, corpus tests, and a maintained upstream engine—not just whether a tool can technically open the file.
