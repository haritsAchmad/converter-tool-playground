# Roadmap

## 0.2 — operational hardening

- [x] Persist minimal job state for restart-safe status reporting.
- [x] Per-IP token-bucket rate limiting and upload quotas.
- [x] Prometheus metrics, request IDs, and OpenTelemetry hooks.
- [x] Layered upload gate: extension chain, magic bytes, MIME, syntax, and active-script rejection.
- [x] Separate API and conversion worker containers with a Redis-backed queue and shared job storage.
- [x] Optional ClamAV stage before the conversion queue; fail closed when enabled.
- [x] Harden the currently-supported structured-data pipeline against known injection/DoS classes: CSV cells are now quote-escaped against formula/DDE injection (OWASP "CSV Injection"), and regression tests confirm the YAML and JSON decoders already reject alias bombs and pathologically deep nesting instead of exhausting resources.
- [x] Bound PNG/JPEG decode memory against a decompression bomb: `image.DecodeConfig`'s declared width/height are now checked against a 100-megapixel ceiling during upload validation, before `image.Decode` ever allocates the full pixel buffer for a conversion.
- [x] Format-specific content-disarm stage for DOCX/PDF/ODT, now that all three landed in 0.3. DOCX (and XLSX/PPTX) and ODT (and ODS/ODP) already got theirs as part of landing those formats: `validateOOXML`/`validateODF` reject macros, embedded objects, and external-non-hyperlink resources at upload time (see the 0.3 entries below). PDF's own equivalent, added here: `validatePDFActiveContent` rejects a PDF carrying an embedded JavaScript name tree, an embedded file attachment, or a document-level `/OpenAction`/`/AA` (additional actions)—the mechanisms that run automatically the instant a document-processing tool opens the file, no user interaction needed. Reuses the same `pdfcpu` structural-validation pass already required for every PDF upload (now via `api.ReadAndValidate`, which returns the parsed `*model.Context` `PageCount`/`Names`/`RootDict` checks need, instead of the plain `api.Validate` that discarded it) rather than a second parse. An embedded file attachment is checked three ways, not just the `/EmbeddedFiles` name tree and `ctx.ListAttachments()` (both of which only look at the catalog's Names dictionary): `validatePDFAnnotationAttachments` also walks every page's `/Annots` for an annotation—most commonly a `/Subtype /FileAttachment` one, PDF's "paperclip icon" attachment—carrying its own `/FS` (file specification) with an `/EF` (embedded file) entry, since that attachment path never has to be registered in the Names dictionary at all (temuan review P2). Attachments are checked this thoroughly, but *actions* stay deliberately scoped to document-level triggers, not exhaustive: a per-object action (a Link annotation's own `/A`, a form field's own `/AA`) isn't walked, since—unlike an attachment, which is inert data sitting in the file regardless of interaction—those actions only fire on explicit user interaction (clicking, editing) that this service's `pdftoppm`-based rendering pipeline never performs, matching this codebase's existing honesty about narrower-than-ideal reject-lists (see `rejectActiveContent`'s `<?php`/`<?=`-only pair). Verified the exact `Names` tree keys (`JavaScript`, `EmbeddedFiles`) and that `XRefTable.Names` gets populated during validation against `pdfcpu`'s own validation source rather than guessed. Regression fixtures are hand-built PDFs with a byte-accurate xref table computed from the actual bytes written (not hand-counted), and were run against `pdfcpu`'s real validator locally to confirm each one is structurally well-formed, not just assumed to be.
- [x] Poison-pill / dead-letter handling for the Redis-backed queue: `requeueActive()` still unconditionally moves everything from `:processing` back onto the main queue on worker startup, but a job now carries a persisted `Attempts` counter (`job.json`, alongside its other state) that a worker increments and durably persists *before* it touches the file—so the count survives a crash mid-conversion, not just a clean failure. Once `Attempts` exceeds `CONVERTBOX_MAX_JOB_ATTEMPTS` (default 3) on pickup, the worker marks the job `failed` with `"exceeded max processing attempts"` and acks it out of `:processing` without ever running the converter again, instead of requeuing it for another crash. Queue-agnostic by construction (state lives in `job.json`, not in Redis), so it also caps retries for the in-process `standalone` queue.
- [x] Optional shared-secret `X-API-Key` authentication on the API and `/metrics`, with the web UI prompting for and remembering the key.
- [x] Documented reverse-proxy config (TLS termination) for deployments reachable beyond localhost, since the API key alone doesn't protect traffic in transit.
- [x] Network egress denial for `worker` and `pdf-worker`—the two services that run an external tool (LibreOffice, ImageMagick, `pdftoppm`, ffmpeg/ffprobe) against untrusted uploaded content—closing the gap both PDF worker isolation and the Office→PDF/Markdown-HTML→PDF entries above explicitly deferred as "still follow-up hardening." Both now sit on `backend`, a new `compose.yaml` network declared `internal: true` (verified against Docker's own compose-file network reference, not guessed): a container on it gets no default gateway configured at all, so there's no route out to the internet or the rest of the LAN, only to whatever else shares that network (`redis`, their one real dependency). `api` stays reachable on its published port by joining both `backend` (to reach `redis`) and the normal `default` network—a multi-homed container's published port keeps working on its non-internal network regardless of also holding an internal one. **Actually verified against a real `docker compose up`** (Docker Desktop wasn't running when PDF worker isolation shipped; it was started for this, with explicit confirmation first, rather than settling for `docker compose config` again): from inside a running `worker`/`pdf-worker` container, `wget http://1.1.1.1` fails with "Network unreachable," while a real CSV→JSON job and a real PDF→PNG job both still flow end to end through `api`'s published port, `redis`, and back out to download—proving the isolation holds without breaking the pipeline it sits in front of. This same real run caught a genuine, previously-undiscovered bug no amount of `docker compose config` validation could have: `pdfcpu` tries to create its own config directory (`~/.config/pdfcpu`) on first use, which panicked with `read-only file system` under `api`'s existing `read_only: true` hardening the moment a real PDF was uploaded—fixed with `api.DisableConfigDir()` in a package `init()`, verified by resubmitting the same PDF job successfully after rebuilding. Real defense in depth beyond this—a separate volume or storage credential, gVisor/Kata-style sandboxing instead of a plain container—remains follow-up hardening.

## 0.3 — more engines

- [x] PDF → PNG/JPEG (every page, up to a 300-page cap, fixed DPI) via poppler's `pdftoppm`, gated behind a second, independent structural validation pass (pdfcpu, which also enforces the page cap) so a hostile PDF has to fool two different parsers, not one. Multi-page output is a ZIP with one `page-N.<ext>` entry per page—including for one-page sources, so the output shape is predictable regardless of page count—since a job still produces exactly one output file.
- [x] Move PDF conversion into its own isolated worker/queue instead of the shared worker pool, for real blast-radius containment if the renderer is ever exploited. A new `pdf-worker` `CONVERTBOX_MODE` dequeues and renders PDF→image jobs off its own Redis queue (`CONVERTBOX_REDIS_PDF_QUEUE`) exclusively; `worker` no longer touches PDF input at all, only every other conversion (Office/ODF/Markdown/HTML→PDF via LibreOffice, images, structured data). `App.queueFor` decides which queue a job lands on at creation time by its input format—enforced in code, not deployment convention, so a job simply can't reach the wrong worker pool. `worker(index int, q jobQueue)` now takes the queue it drains as a parameter rather than always reading `a.queue`, which is what makes a worker's queue scope structural rather than just "shouldn't happen in practice." `standalone` mode (no Redis, a single process) reuses one local queue for both roles, since a single process has nothing to isolate a second queue from—`newQueuesForMode` documents the queue shape each of the four `Mode` values gets. `compose.yaml` gains a `pdf-worker` service (same image as `worker`—`pdftoppm` is already in it—just a different `CONVERTBOX_MODE` and a lighter resource envelope, since it never runs memory-hungry LibreOffice); this is a deployment-facing change, not just a code one—an existing split deployment needs the new service added to actually get the isolation. See the README's new "PDF worker isolation" section for what this does and doesn't protect against (process/queue isolation, not a sandbox—separate storage credentials, gVisor/Kata-style sandboxing remain follow-up hardening; network egress denial was closed shortly after, see the network egress denial entry below) and the single-instance-per-service caveat that already applied to `worker` and now applies to `pdf-worker` too (`requeueActive()`'s unconditional per-queue requeue-everything-in-:processing-on-startup isn't safe with multiple replicas of the same service).
- [x] PDF as an output format, for images: PNG/JPEG/WebP → PDF via pdfcpu's pure-Go image import (no external tool, unlike every other PDF or WebP conversion pair here)—one page, sized to the source image at 150 DPI.
- [x] PDF as an output format, for documents: Markdown/HTML → PDF via the same headless LibreOffice engine and per-job profile isolation Office→PDF uses (`convertViaLibreOffice`, shared by both). Markdown is rendered to HTML first with goldmark in its default *safe* mode (raw HTML in the source is dropped, not passed through) rather than handed to LibreOffice directly, since a bundled headless LibreOffice can't be relied on to have its own Markdown filter. Unlike the existing pure-Go HTML↔Markdown text conversion, this pair actually renders the document with a real layout engine that resolves references, so it's gated by `validateHTMLForPDF`, which parses the document (`golang.org/x/net/html`) rather than pattern-matching the raw bytes and rejects `<script>`/`<iframe>`/`<object>`/`<embed>`/`<base>` tags and inline event handlers outright. Every resource reference (`src`/`srcset`/`poster`/`background`/`formaction`/`action`/`<object>` `data`/`<link>` `href`/CSS `url()`) is accepted only as an inline `data:` URI—not just an external `http(s)` URL blocked, everything else rejected by default—since LibreOffice resolves a relative or absolute local path against the document's real on-disk location and a job's per-job working directory is not a sandbox (temuan review P1: an earlier version allowed same-directory-relative references on the mistaken assumption they had nothing to resolve against, which missed that `../` can walk into a sibling job's files or anywhere else the worker can read, and checked the raw HTML text for a scheme prefix, which an HTML-entity-encoded `src="&#104;ttp://127.0.0.1/probe.png"` slips past a real parser doesn't). An ordinary `<a href>` hyperlink is left alone, its target never fetched (mirrors the OOXML validator's own hyperlink allowance). The accepted `data:` URIs are themselves a closed allowlist of raster image formats (PNG/JPEG/GIF; not WebP, which this codebase has no Go-native decoder to dimension-bound, the same gap `validateUpload` already has for it), cross-checked against the actual decoded bytes' signature and bounded by the same `maxImageDecodedPixels` ceiling an ordinary image upload gets—accepting *any* `data:` URI isn't enough (temuan review P1, round 3): a `data:text/css;base64,...` stylesheet used to pass that check, but LibreOffice parses its decoded content as an ordinary stylesheet just like a `<style>` block, so a nested external `url(...)` inside it reached LibreOffice's fetch path unchecked; `image/svg+xml` is excluded too, since an SVG can embed its own `<script>`. No LibreOffice flag exists to deny outbound network access at the application level per Ask LibreOffice's own forum; network-level denial (the same `worker` sits behind regardless of which conversion it's running) is covered by the network egress denial entry below. Structured data → PDF is lower priority and not part of this slice.
- [x] DOCX/XLSX/PPTX → PDF via headless LibreOffice with per-job profiles, bounded OOXML package validation, and rejection of macros, embedded objects, and external resources. Network egress denial for the `worker` container this runs in landed later, in 0.2's network egress denial entry.
- [x] Office-to-PDF fidelity controls: `pdfMode=standard` (default, no export filter options—today's behavior unchanged) vs `pdfMode=optimized` (`SinglePageSheets` for Calc, `EmbedStandardFonts` and `ReduceImageResolution`/`MaxImageResolution=150` for all three), exposed via the API and a web UI selector shown only for Office→PDF. Verified against LibreOffice's own filter registry and PDF-export-parameters documentation rather than guessed—getting a filter option name wrong means it silently no-ops. Orientation and print-area turned out to *not* be independently controllable via export filter data at all (they're read from the source document's own page style, not overridable at export time), so those aren't part of this—only what's actually achievable shipped, nothing implied by the original wording that wasn't.
  - [x] Regression corpus: real (not placeholder-content) DOCX and multi-sheet XLSX fixtures actually run through LibreOffice—a baseline this codebase didn't have at all before (only OOXML *package-structure* validation was tested, never an actual conversion). Locks in that `optimized` mode's `SinglePageSheets` guarantee holds (a 3-sheet workbook always comes back as exactly 3 PDF pages) and that both modes produce structurally valid PDFs (pdfcpu-validated).
  - [ ] Impress/PPTX regression fixture: skipped for now. A minimal-but-schema-valid PPTX needs a slide → slideLayout → slideMaster → theme relationship chain with real content in each (theme1.xml alone needs a full 12-color scheme, font scheme, and 3-tier fill/line/effect format scheme)—considerably more scaffolding than DOCX/XLSX, and with no local LibreOffice available to verify a hand-built fixture actually opens, shipping one unverified risked a corpus test that's silently wrong rather than useful. The filter name (`impress_pdf_Export`) is verified against LibreOffice's own filter registry and covered by a pure-Go unit test; the conversion code path is 100% shared with DOCX/XLSX. Pick up if/when there's a LibreOffice-capable dev environment to verify a real fixture against, or a maintained minimal-PPTX generator worth depending on.
  - [ ] Writer header/footer overflow and Impress text-fit/slide-layout *checks* (as opposed to the controls above) would need rendering the PDF to pixels and comparing against page bounds—out of scope for this slice, which covers the concrete, filter-data-level controls the roadmap wording anticipated.
- [x] ODT/ODS/ODP → PDF via the same LibreOffice pipeline as Office→PDF (`convertOffice`/`convertViaLibreOffice`, always called with `pdfMode=""` since its fidelity filter options were verified against OOXML's filter registry only—see the Office-to-PDF fidelity controls entry above—not ODF's, so `odfFormats` is deliberately kept separate from `officeFormats` rather than silently inheriting `pdfMode`). `validateODF` is `validateOOXML`'s counterpart: the same entry-count/uncompressed-size/decompression-ratio bounds and zip-slip rejection, adapted to ODF's own package layout—macros live under top-level `Basic/`/`Scripts/` directories (verified against the OpenOffice/LibreOffice Basic IDE's documented library storage convention) rather than a `vbaProject.bin` part, and an embedded object is a numbered `ObjectN/` subpackage rather than an `/embeddings/` part, both rejected outright. External resource references get a *stricter* policy than OOXML's own denylist-of-external-non-hyperlink-resources: this codebase found no unambiguous confirmation that every ODF-consuming LibreOffice code path resolves a relative `xlink:href` purely against the package's own entries rather than ever falling through to the filesystem the way the Markdown/HTML→PDF path turned out to—so every `xlink:href` outside a `text:a`/`draw:a` element's *own* `href` is accepted only when it names a real entry already present in that same, already-validated ZIP package, never anything with a scheme, a leading `/`, or a `..` segment, matched against its percent-decoded form. Two temuan review rounds tightened this further: round 1 exempted every `href` anywhere inside a hyperlink's subtree rather than just the hyperlink element's own target, so an external image nested inside a `draw:a` (a linked logo, say) slipped through; round 2 compared against the href's raw, still-encoded text, so an ordinary reference like `Pictures/my%20photo.png` to a real package entry containing a space was wrongly rejected. The package's own mandatory first `mimetype` entry (stored, uncompressed, no extra field, per the OASIS OpenDocument Package spec) is checked twice: a fixed-byte-offset signature check at upload time (mirroring the existing PNG/JPEG/OOXML magic-byte checks) and again against the real ZIP entry during structural validation. A real end-to-end LibreOffice conversion corpus test is deferred for the same reason the Impress/PPTX regression fixture above was: no LibreOffice-capable dev environment was available here to verify a hand-built ODT/ODS/ODP fixture actually opens, and shipping one unverified risks a corpus test that's silently wrong rather than useful; static package validation and a fake-LibreOffice "reaches conversion" pipeline test cover what can be verified without one.
- [ ] Experimental PDF → Office extraction; do not advertise this as layout-perfect or implement it by merely opening PDF in LibreOffice Draw.
- [x] Audio through FFmpeg (MP3/WAV/FLAC/Ogg Vorbis-Opus) with probe limits and codec whitelists. Every upload is probed with `ffprobe` before conversion (`validateAudio`) and rejected unless it has exactly one audio stream on a fixed per-container codec whitelist (`audioCodecWhitelist`—libmp3lame/libvorbis availability confirmed against Alpine's actual `ffmpeg` package, not assumed), a duration under 4 hours, and no extra video/subtitle/data stream—except an attached-picture cover-art stream, which real-world MP3/FLAC files commonly carry and would otherwise be collaterally rejected. FFmpeg's network-capable input protocols are disabled on every invocation, both the probe and the real conversion: `-protocol_whitelist file` (verified against real SSRF/LFI writeups for ffmpeg's HLS/concat demuxers, not guessed) restricts protocols to local file I/O only, and `-f <format>` additionally forces the exact expected demuxer rather than leaving format selection to content-based auto-detection—closing off the same "file merely named `.mp3` but structured as an HLS playlist" trick the protocol whitelist alone doesn't fully prevent (a demuxer's own nested references still resolve through whatever's whitelisted). `-analyzeduration`/`-probesize` are pinned to explicit values rather than left to ffmpeg's own version-dependent defaults. See the README's new "FFmpeg hardening" section. Video (below) was deliberately scoped out of this slice and picked up separately, once its own, meaningfully larger surface area (multi-stream/subtitle-track/chapter-metadata) could get the same deliberate treatment rather than being attempted alongside audio.
- [x] Video through FFmpeg (MP4 H.264/AAC, WebM VP8-VP9/Opus-Vorbis), the follow-up slice the audio entry above deferred. Reuses the exact same engine and hardening (`ffmpegHardeningArgs`, `-f <format>`, `-protocol_whitelist file`, pinned `-analyzeduration`/`-probesize`—see the README's "FFmpeg hardening" section), extended rather than duplicated: `validateVideo`/`convertVideo` share `ffmpegHardeningArgs` with `validateAudio`/`convertAudio` (renamed from `audioProbeArgs` now that it's genuinely shared), and `ffprobeStream` gained `Width`/`Height` fields both use. libx264/libvpx/libopus availability was confirmed directly against this project's exact `alpine:3.22` `ffmpeg-libavcodec` package dependency list (checked on pkgs.alpinelinux.org, not assumed)—AAC needs no external library, ffmpeg's own encoder covers it. `mp4`/`webm` aren't literally ffmpeg's own input-side *demuxer* names (those are the combined `mov,mp4,m4a,3gp,3g2,mj2` and `matroska,webm`), but empirically confirmed against a real ffmpeg binary that its format-name resolution accepts them as input aliases into those anyway, rather than assuming from the `-formats` listing (which would have suggested otherwise). Deliberately narrower than audio, matching why video was scoped out in the first place: exactly one video stream and at most one audio stream (silent video is valid; any subtitle/data stream, or more than one of either, is rejected outright, with no cover-art-style exception the way audio has for attached pictures), a 720p pixel ceiling, and a 60-second duration cap—chosen so a job stays plausibly within reach of this project's existing (audio/document-sized) job-timeout model rather than adding a video-specific one, since actual encode time still depends on content complexity and available CPU, not just duration/resolution. `newConverter`'s Dockerfile/package dependencies needed no changes at all: the same `ffmpeg` package the audio slice already added bundles every codec this needs. Verified end to end with real ffmpeg/ffprobe (installed locally via scoop for this, same as the audio `-nostdin` fix): a live CLI prototyping pass nailed down the exact command structure and confirmed the `mp4`/`webm` input-format-alias behavior *before* any Go code was written, and the full regression suite—including real MP4↔WebM round-trip conversion and a full HTTP create-to-worker-to-completed pipeline test, using fixtures ffmpeg itself generates via its `lavfi` test sources rather than hand-built bytes (impractical for a codec this complex, unlike the audio slice's hand-built WAV)—passes for real, not just via the pure-Go codec-whitelist table tests.
- [x] SVG → PNG/JPEG, pure Go, always available. Two deliberately independent layers, matching this line's own wording: `validateSVG` (the sanitizer, upload-time) parses with `encoding/xml` and rejects outright a non-`<svg>` root, `<script>`/`<foreignObject>`/`<image>`/SMIL-animation/`<iframe>`/`<object>`/`<embed>`/`<audio>`/`<video>`, any inline event-handler attribute, any `javascript:` URI, any `href`/`xlink:href` other than a same-document `#fragment` or a safe inline `data:` image (`isSafeDataURI`, shared with the Markdown/HTML→PDF validator), any CSS `url()` to anything but a safe `data:` URI (`validateCSSForPDF`, also shared), and a leading DOCTYPE outright (no legitimate use for one here). `convertSVG` (the rasterization boundary, conversion-time) renders with `github.com/srwiley/oksvg`+`rasterx`, a pure-Go renderer verified directly against its source—not assumed—to implement only path/shape/gradient/group elements plus a same-document-only `<use>`, with no scripting engine and no `net`/`net/http`/`os/exec` import anywhere in either package, so even an SVG that somehow slipped past the sanitizer can only fail to render the parts this renderer doesn't understand, never execute or fetch anything, independent of the sanitizer by construction rather than by trusting it caught everything. `govulncheck` found no advisories against either dependency. The raster canvas is bounded by the same `maxImageDecodedPixels` ceiling an ordinary PNG/JPEG upload gets, checked before allocation, with a fixed 512x512 fallback for the (confirmed real, not hypothetical) case of a root `<svg>` declaring no width/height/viewBox at all. WebP isn't offered as an output here for the same reason it isn't for PDF→image: no pure-Go WebP encoder in this project's dependencies. Verified with real hostile fixtures (script injection, event handlers, plain and entity-encoded `javascript:` URIs, external `<image>`/`<use>` references, external CSS, a DOCTYPE entity-bomb payload) confirmed rejected and real benign fixtures confirmed rasterized with pixel-level assertions on the decoded output, not just "no error". This work also surfaced and fixed an unrelated, genuine pre-existing bug it happened to make reproducible: `store.persist()`'s `os.Rename` had no retry against a transient Windows "Access is denied" while a concurrent status poll had `job.json` open for reading, silently stranding a job's on-disk status (most visibly its final Completed/Failed transition) forever—see CHANGELOG.md's Fixed section.
